# Mission Reflection

Working with containers helped me understand that containers are not completely independent from the host server. Although each container has its own processes and environment, containers still share important host resources such as CPU, memory, storage, and network resources. Because of this, a container may appear healthy while the host system is actually running low on RAM or disk space. If the host runs out of resources, multiple containers can become slow, unstable, or even crash at the same time. This showed me why monitoring the host server is just as important as monitoring individual containers.

If a user reports that they cannot log in to an application, I would first investigate the application's container logs using `docker logs`. The logs can provide useful information about requests received by the application, HTTP status codes such as `401`, `403`, and `500`, and error messages generated by the application. I could also use `docker logs -f` to follow the logs in real time while the user attempts to log in again. This would allow me to identify exactly what happens during the failed login attempt. For example, the problem could be caused by an incorrect password, an authentication service failure, a database connection problem, or an application error. Instead of immediately changing settings or restarting services, I can use the logs as evidence to determine the actual cause of the problem.

I also learned the difference between **logs and metrics**. Logs are records of individual events that occur within a system. I can think of them like security camera footage because they provide details about what happened and when it happened. Metrics, on the other hand, are numerical measurements collected over time, such as CPU utilization, memory usage, disk usage, network traffic, and request rates. Metrics help me understand the overall health and performance of a system. For example, a metric may show that memory usage has suddenly increased, while the logs can help explain which application or event caused the increase. In this way, metrics can tell me that something is wrong, while logs can provide clues about why it happened.

Monitoring becomes even more important when managing a large number of containers. Manually checking thousands of containers would be inefficient and impractical. Enterprises therefore use monitoring and observability tools such as **Prometheus** and **Grafana**. Prometheus can automatically collect and store metrics from servers, applications, and containers, while Grafana can display those metrics through dashboards and visualizations. Alerting systems can also notify engineers when important values exceed predefined thresholds, such as when CPU or memory usage becomes too high or when application error rates increase. This allows problems to be detected and investigated before they significantly affect users.

Through this mission, I became more comfortable using command-line tools for system monitoring and troubleshooting. I can now check memory usage with `free -h`, examine disk space with `df -h`, monitor running processes with `top`, and inspect container activity using Docker commands such as `docker logs` and `docker stats`. More importantly, I learned that troubleshooting should be based on evidence rather than assumptions. When I encounter a problem, I should examine the available information, such as error messages, logs, resource usage, and command output, before deciding what action to take.
